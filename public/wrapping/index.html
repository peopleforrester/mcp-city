From "Governing MCP for a Workforce the Size of a City", MCP Dev Summit Toronto, 6 October 2026

We wrapped MCP servers in MCP servers. So did you.

A wrapper is an MCP server with no tools of its own: when the client asks for the tool list or calls a tool, it forwards the request to the real server behind it, relays the answer back, and does something useful on the way through.

Why

  1. The server does not meet our security standards. It carries no authorization, so the wrapper validates the token and decides, per tool, whether this caller may use it. Of 7,973 live remote servers measured in 2026, 40.55 percent expose tools with no authentication at all.
  2. Credentials must not cross from client to server. The server needs a credential the client must never hold, so the wrapper holds it.
  3. A hundred tools offered; nine presented. The wrapper filters the list so the model sees what it needs.
  4. Reads and writes split into separate servers. A tool that does both is rejected by Anthropic's connector review. When a server shipped one, we wrapped that server twice: one wrapper exposes only the reads, one only the writes. Two risk levels, two approvals.
  5. The wrong transport. The server speaks stdio and the clients speak HTTP, or the other way round, so the wrapper bridges it.
  6. Every call logged, rate limited and traced.
The one test of whether a wrapper is built right: is the credential that reaches the upstream different from the one the client sent? The specification is explicit: the MCP server MUST NOT pass through the token it received from the MCP client.

Tools that do it

  • FastMCP 4: create_proxy(), one call
  • Stacklok ToolHive: MCPRemoteProxy with OIDC, Cedar policies, token exchange, audit, tool filtering
  • Agent Router (formerly Envoy AI Gateway, now an Agentic AI Foundation project): aggregation, OAuth, upstream key injection, tool filtering
  • TBXark mcp-proxy: one endpoint, many upstreams
  • mcpwrapped: tool filtering only
