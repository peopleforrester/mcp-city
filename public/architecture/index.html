The architecture, done properly

The simple version:

A person→A device→An agent→One gate: proxy and registry→The tools

Everything below is that gate, done properly. Pinch to zoom; the picture is the slide at full size.

How to read it

Managed device (pink)
The user, the agent (an MCP client), the client policy that says which servers may load, and the OS and app policies that close the side doors: Outlook's automation guard set to deny, Edge remote debugging off.
Tool traffic (orange)
A proxy answers how the request reaches the server; the gateway answers whether this caller is allowed (identity, authorization, policy, rate limits, enforced once). Behind it the service boundary, the MCP server wrapped where needed and holding an exchanged token, never the user's, and the tool. Third-party hosted MCP sits off the gateway, acting under the user's own grant.
Model traffic (purple)
The AI gateway chooses model and provider and enforces quotas and guardrails on the way to the LLM providers.
Control plane (green)
The MCP registry (what exists, who owns it) feeds the allow list and the routing table; the model registry feeds the AI gateway; the identity provider and workload identity tell the gateway who and which agent is calling; GitOps with admission control means no unsanctioned server lands.
Audit (black)
Everything that goes through a gateway is logged and joined by trace context.
The two dashed pink lines
The point of the talk: shell and COM automation to Outlook, and browser remote debugging to Teams. They never touch any of it.
